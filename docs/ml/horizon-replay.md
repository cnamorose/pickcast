# 10분 예상 판매량과 시뮬레이션 재생 파일

판매자용 시뮬레이션·게임은 "앞으로 10분 동안 무엇이 몇 개 팔릴지"를 보여줘야 한다. v3 모델의 확률은 "예측 시점 이후 언젠가 그 상품을 살 확률"이라 기간이 없다. 이 확률을 **10분 안에 살 확률**로 바꾸는 방법을 valid(7월)로 만들고 test(8~9월)로 확인했다. 그 결과로 시뮬레이션 화면이 재생할 하루치 파일을 만들었다.

모델(v3)은 다시 학습하지 않았다. 바꾼 것은 확률을 기간으로 나누는 계산뿐이다.

## 1. 왜 10분인가

모델은 이미 들어와서 상품을 보거나 담은 고객만 예측할 수 있다. 예보 기간이 길수록 그 사이 새로 들어온 고객의 판매가 늘어 모델이 볼 수 없는 판매가 커진다. test 구매 4,838건에서, 아무 구간을 잡았을 때 구간 시작 전에 이미 보거나 담은 상품의 판매 비율은 다음과 같다.

| 예보 기간 | 미리 볼 수 있는 판매 |
| --- | ---: |
| 10분 | 72.1% |
| 30분 | 48.5% |
| 1시간 | 36.2% |
| 3시간 | 22.8% |

구매마다 그 상품을 처음 보거나 담은 뒤 산 시간 L을 재고, 무작위 구간에서 구간 시작이 첫 행동 뒤일 확률 min(1, L / 기간)을 평균했다. 보거나 담지 않고 산 구매는 0이다. 10분 행은 `evaluate_horizon.py`가 계산하고, 나머지 행은 같은 방식으로 따로 계산했다.

10분이면 판매 대부분을 미리 볼 수 있어 10분으로 정했다. 아직 들어오지 않은 고객의 판매(약 29%)는 예측에 넣지 않는다. 과거 평균 같은 단순 추정을 더할 수 있지만 AI 예측이 아니어서 뺐다.

## 2. 방법: 10분 판매 비율

valid 기간을 10분 간격으로 재생한다. 시각 t마다 그때 쇼핑 중인 고객(마지막 행동이 24시간 안)의 후보 상품을 본다. 후보마다 t 이전 마지막 예측 시점의 v3 확률 p를 쓴다. 후보는 두 가지로 나눈다.

- 그 시각까지 그 상품을 장바구니에 담았는지
- 마지막 행동 뒤 몇 분이 지났는지 (경과 시간 구간 20개, 마지막 행동 직후일수록 촘촘하게)

나눈 묶음마다 다음 비율을 구한다.

> 10분 판매 비율 r = (t, t+10분]에 실제로 팔린 수 ÷ 그 후보들의 p 합

10분 안에 살 확률은 **min(1, p × r)** 이다.

- 그 10분 사이 고객이 더 둘러보거나 담는 경우도 그대로 들어간다. "지금 이 상태인 상품이 다음 10분 안에 팔리는가"를 직접 센 값이다.
- 시각마다 후보의 최신 상태 하나만 세므로, 같은 구매를 여러 번 세지 않는다.
- t 전에 이미 산 상품은 빼고, 같은 사용자·상품은 첫 구매만 센다.

valid에서 구한 비율의 일부다(모델 확률 1당, 다음 10분 판매).

| 마지막 행동 뒤 | 담은 상품 | 담지 않은 상품 |
| --- | ---: | ---: |
| 0~1분 | 0.542 | 0.141 |
| 3~5분 | 0.383 | 0.049 |
| 10~15분 | 0.113 | 0.023 |
| 30~45분 | 0.017 | 0.002 |
| 2시간 뒤 | 0.001 이하 | 0.001 이하 |

예를 들어 모델 확률 10%인 상품을 방금 담았다면 10분 안에 팔릴 확률은 약 5.4%다. 비율은 `ml/models/product_purchase_v3/horizon_rates.json`에 있다.

## 3. 처음 쓴 방법과 실패

처음에는 **구매 지연 분포**를 썼다. 정답 1인 행(결국 산 행)에서 예측 시점부터 사기까지 걸린 시간 분포 F를 구했다. 10분 안에 살 확률은 p × (F(e+10) − F(e)) / (1 − p × F(e))로 계산했다.

test에서 예상 판매 8,801건, 실제 3,427건으로 2.6배 높게 나왔다. 담지 않은 상품은 5.8배였다. 10분 구간 오차(1.011)는 직전 10분 실제 판매를 그대로 쓰는 단순 예측(0.683)보다도 나빴다.

valid에서도 똑같이 2.4배 높게 나왔다. 기간이 바뀌어서가 아니라 방법의 문제였다.

- F는 "결국 산 경우 언제 샀는가"라 대부분 예측 시점 직후에 몰려 있다.
- 고객이 사지 않고 계속 둘러보면 예측 시점이 새로 생길 때마다 "곧 산다"가 다시 적용됐다.
- 오래 둘러보는 고객일수록 같은 구매를 여러 번 예상했다.

두 번째로, 마지막 행동 뒤 아무것도 하지 않은 시간당 구매 발생률을 구했다. 이 방법은 고객이 담고 나서 사는 경우를 "담은 상품의 판매"로 세었다. 그래서 그 전 시각에서 본 "담지 않은 상품이 10분 안에 팔림"을 놓쳤다. valid에서 담지 않은 상품을 3.6배 낮게 예측했다(165 vs 592). 이 방법은 test를 보기 전에 valid에서 버렸다.

세 번째 방법(2절)은 화면에 띄울 값, 즉 지금 상태에서 다음 10분 판매를 valid에서 직접 셌다.

**test를 본 순서**: 첫 방법의 test 결과를 본 뒤 방법을 바꿨다. 바꾸는 과정에서는 valid만 봤고, test는 세 번째 방법으로 한 번 더 확인했다. 첫 결과는 `ml/data/product_purchase_time/horizon/test_metrics_first_attempt.json`에 남겼다.

| 지표 | 값 |

## 5. 시뮬레이션 재생 파일

`build_replay.py`가 test 하루를 1분 간격으로 계산해 `ml/results/replay/날짜.json`에 저장한다. 시뮬레이션 화면(백엔드 재생 API)이 이 파일을 읽는다.

| 내용 | 설명 |
| --- | --- |
| `snapshots.shoppers` | 1분마다 최근 30분 안에 보거나 담은 고객 수 |
| `snapshots.carting` | 1분마다 최근 30분 안에 담은 고객 수 |
| `snapshots.expected_next_10m` | 1분마다 다음 10분 예상 판매 합 |
| `snapshots.top_items` | 1분마다 예상 판매 상위 10개 상품: 상품, 예상 판매, 1개 이상 팔릴 확률, 후보로 둔 고객 수 |
| `events` | 그날의 조회·담기·구매: 시작부터 초, 고객 번호, 종류(v/c/b), 상품 |
| `purchases` | 구매마다 산 직전 예측 시점의 확률, 후보 중 순위, 후보 수, 예측 시점부터 걸린 분 |

- 고객 번호는 그날 처음 나온 순서로 1부터 다시 매겼다. 시각은 UTC다(이 데이터는 UTC 오후 4시~밤 10시에 구매가 몰린다).
- test 사용자만 넣었다. 여러 기간에 걸친 고객(구매의 약 26%)이 빠져 실제 쇼핑몰보다 판매가 적다.
- `purchases`의 순위는 산 상품을 방금 보거나 담은 시점(결제하러 들어간 조회)이면 한 시점 앞의 예측으로 센다. 보거나 담지 않고 산 구매는 확률·순위가 없다.

| 날짜 | 고른 이유 | 고객 | 기록 | 구매 | 10분 예상 합 | 미리 본 구매 중 1순위 | 1~3순위 | 크기 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2015-08-17 (월) | 구매가 많은 날 | 11,547 | 18,276 | 156 | 109.2 | 84 / 141 | 120 / 141 | 0.85MB |
| 2015-08-07 (금) | 평범한 날 | 10,456 | 16,073 | 104 | 93.0 | 63 / 96 | 85 / 96 | 0.79MB |

- 10분 예상 합은 10분 간격 시각의 예상 판매를 더한 값이다. 예측 대상 비율(약 71%)만큼 실제 구매보다 적은 것이 맞다. 8/17은 156건의 71%인 약 110건과 비슷하고, 8/7은 약 74건보다 높게 나왔다.
- 1순위 비율(60~66%)이 [test의 구매 직전 1순위 정답률](time-split-results.md)(75.4%)보다 낮다. test 지표는 고객의 첫 구매만 세지만, 여기서는 한 번에 여러 상품을 산 경우도 상품마다 센다. 같이 산 상품 중 하나만 1순위가 될 수 있다.

## 6. 한계

- 아직 들어오지 않은 고객과 보거나 담지 않고 산 판매(약 29%)는 예측하지 않는다. 화면에는 "지금 쇼핑 중인 고객 기준"이라고 밝혀야 한다.
- 비율은 7월 하나로 만들었다. test에서 담은 상품을 13% 높게 예측했는데, 기간에 따라 구매 속도가 다를 수 있다.
- 시각대·요일은 나누지 않았다.
- 10분 구간에 평균 0.5건이라 구간 하나의 예상은 흔들린다. 1시간 단위나 상품 순위로 보는 편이 안정적이다.

## 7. 실행 방법

프로젝트 최상위 폴더에서 실행한다. 시간 분할 학습 데이터(`extended_rows/`)와 v3가 있어야 한다.

```powershell
$env:PRODUCT_PURCHASE_DIR = "product_purchase_time"
$env:PYTHONIOENCODING = "utf-8"

.\ml\.venv\Scripts\python.exe ml/product_purchase/fit_horizon_rates.py --version v3            # valid로 비율 (버전 폴더에 저장)
.\ml\.venv\Scripts\python.exe ml/product_purchase/evaluate_horizon.py --version v3 --split valid
.\ml\.venv\Scripts\python.exe ml/product_purchase/evaluate_horizon.py --version v3 --split test  # 결과가 있으면 실행되지 않음
.\ml\.venv\Scripts\python.exe ml/product_purchase/build_replay.py --version v3 --date 2015-08-17 --date 2015-08-07
```

| 파일 | 내용 |
| --- | --- |
| `product_purchase/horizon.py` | 10분 판매 비율 계산(`RateCounter`)과 10분 확률(`within_horizon`) |
| `product_purchase/horizon_rows.py` | 행 준비(확률, 첫 구매 시각, 다음 예측 시점)와 일정 간격 재생(`window_pairs`) |
| `product_purchase/fit_horizon_rates.py` | valid로 비율을 만들어 `horizon_rates.json`에 저장 |
| `product_purchase/evaluate_horizon.py` | valid·test 확인 (`ml/data/product_purchase_time/horizon/`) |
| `product_purchase/build_replay.py` | 재생 파일 (`ml/results/replay/`) |
