# 피크타임 트래픽 우선 처리: 시뮬레이션 결과

확장 기능 3. 서버가 감당 못 할 만큼 요청이 몰렸을 때, 구매 확률이 높은 고객의 요청을 먼저 처리하면 선착순보다 실제로 산 고객을 더 많이 지킬 수 있는지 RetailRocket 기록을 재생해 비교했다. 실제 서버에 부하를 걸지 않는다. α는 valid로 정하고 test로 한 번 확인했다.

코드: `ml/product_purchase/peak_simulation.py` (요약 파일이 이미 있으면 실행되지 않음)

```powershell
.\ml\.venv\Scripts\python.exe ml/product_purchase/peak_simulation.py
```

결과: `ml/results/peak_simulation.json` (요약, Git 관리), `ml/data/product_purchase/peak_simulation.json` (전체)

## 방법

**요청 재생**
- 조회 시점 하나를 서버 요청 하나로 본다. 요청의 우선순위 점수는 그 시점 고객의 구매 확률 중 최댓값을 기준 확률(한 번 본 상품) 대비 배수(lift)로 바꾼 값이다. 서비스 모델 v2를 썼다.
- 구간마다 가장 붐비는 100개 시간대를 골라, 1시간을 60초로 압축해 각각 재생했다. 붐비는 시간대도 시간당 요청이 300개 안팎이라 압축해야 몰리는 상황이 된다.
- 서버는 1초에 (평균 도착 수 ÷ 1.5)개만 처리한다. 항상 1.5배 과부하다.
- 10초 넘게 기다린 요청의 고객은 떠나고, 그 고객의 이후 요청은 들어오지 않는다.
- 구매 고객: 재생 구간 안의 요청 중 이후 정답(그 상품을 산다)이 있는 고객
- 확률 낮은 고객: 모든 요청의 점수가 1.5배 미만인 고객 (구경 중 수준)

**처리 방식**

| 방식 | 처리 순서 |
| --- | --- |
| 선착순 (`fifo`) | 먼저 온 요청부터 |
| 확률 우선 (`priority`) | 점수가 높은 요청부터 |
| 확률 우선 + 에이징 (`aging`) | 점수 + α × 기다린 시간이 높은 요청부터 |

에이징이 없으면 확률이 낮은 고객은 계속 밀릴 수 있다. 모든 요청이 같은 속도로 나이를 먹으므로 "점수 − α × 도착 시각"으로 정렬해도 순서가 같아, 힙에 한 번 넣은 뒤 다시 정렬하지 않는다.

**α 선택 기준 (valid, 결과를 보기 전에 정함)**: 확률 낮은 고객이 떠난 비율이 선착순보다 5%p 넘게 늘지 않는 α 중 지킨 구매 고객 비율이 가장 높은 것. 처음에는 α를 2까지만 봤는데 기준을 만족하는 값이 없어 5~100을 추가했다. 기준은 바꾸지 않았다.

## 결과

### valid (α 선택) — 구매 고객 283명, 고객 16,539명

| 방식 | α | 지킨 구매 고객 | 전체 이탈 | 확률 낮은 고객 이탈 |
| --- | ---: | ---: | ---: | ---: |
| 선착순 | - | 58.3% | 19.1% | 14.6% |
| 확률 우선 | 0 | 82.3% | 37.7% | 44.1% |
| 에이징 | 0.5 | 87.6% | 30.4% | 35.0% |
| 에이징 | 5 | 80.9% | 24.0% | 24.7% |
| 에이징 | 10 | 71.7% | 21.9% | 20.6% |
| **에이징 (선택)** | **20** | **62.9%** | 20.6% | **17.9%** |
| 에이징 | 100 | 60.1% | 19.4% | 15.3% |

선택 기준(확률 낮은 고객 이탈 19.6% 이하)을 만족하는 α 중 구매 고객을 가장 많이 지킨 α=20을 골랐다.

### test (한 번 확인) — 구매 고객 319명, 고객 16,704명

| 방식 | α | 지킨 구매 고객 | 전체 이탈 | 확률 낮은 고객 이탈 |
| --- | ---: | ---: | ---: | ---: |
| 선착순 | - | 57.1% | 18.6% | 14.1% |
| 확률 우선 | 0 | 82.1% | 39.0% | 45.5% |
| 에이징 | 0.5 | 86.5% | 31.2% | 35.9% |
| 에이징 | 5 | 79.9% | 24.0% | 24.7% |
| 에이징 | 10 | 69.0% | 22.1% | 20.9% |
| **에이징 (선택)** | **20** | **62.7%** | 20.1% | **17.4%** |
| 에이징 | 100 | 57.7% | 18.7% | 14.6% |

**선택한 α=20**: 선착순보다 구매 고객을 **+5.6%p** 더 지키고(57.1% → 62.7%), 확률 낮은 고객 이탈은 **+3.3%p** 늘었다(14.1% → 17.4%). valid와 거의 같은 결과다.

## 해석

- **이득과 손해를 맞바꾸는 관계다.** 서버 처리량은 그대로라 누군가를 먼저 처리하면 다른 누군가가 밀린다. 구매 고객을 더 지킬수록 확률 낮은 고객이 더 떠난다. α 하나로 그 사이의 지점을 고를 수 있다.
- **공정성을 더 양보하면 효과가 커진다.** test에서 α=5는 구매 고객을 +22.9%p 지키지만 확률 낮은 고객 이탈이 +10.6%p 늘고, α=0.5는 +29.5%p / +21.8%p다. 이번에는 미리 정한 기준대로 보수적인 α=20을 골랐다.
- **에이징이 확률 우선보다 구매 고객을 더 지키는 구간이 있다** (α=0.5~1). 나중에 사는 고객도 첫 조회 때는 점수가 낮아서, 에이징이 없으면 쇼핑 초반에 밀려 떠나 버리기 때문이다.
- **전체 이탈은 선착순이 가장 적다.** 확률 우선은 떠나는 고객 수 자체를 늘린다. 매출이 아니라 방문 고객 수가 목표라면 선착순이 낫다.

## 윤리적 고려

고객을 구매 확률로 줄 세우는 방식이라 "살 것 같은 사람만 대우받는다"는 비판이 가능하다.

- **완화 장치**: 에이징으로 오래 기다린 고객도 결국 처리되고, 과부하일 때만 동작하며, 거절하지 않고 늦출 뿐이다. 선택 기준에 확률 낮은 고객의 이탈 상한을 둬 손해의 크기를 숫자로 묶었다.
- **입력**: 확률은 조회 행동만으로 계산한다. 나이, 성별, 지역 같은 개인 정보는 쓰지 않아 특정 집단을 차별할 입력은 없다.
- **현실의 방식**: 실제 서비스에서는 사람이 아니라 요청 종류(결제 요청을 상품 목록보다 먼저)로 우선순위를 두는 경우가 흔하고 논란이 적다. 이번 실험은 그보다 한 걸음 나가 고객의 구매 가능성을 쓴 것이며, 실제 적용 전에는 공정성 기준(대기 시간 상한, 이탈 상한)을 먼저 정해야 한다.

## 한계

- **"처리만 되면 원래대로 샀을 것"이라는 가정**이 깔려 있다. 기다리다 떠난 고객이 실제로 안 샀을지는 확인할 수 없고, 실제 효과는 A/B 테스트가 필요하다.
- 구매 고객이 구간마다 300명 안팎이라 지킨 비율은 ±3%p 정도 흔들릴 수 있다. α=20의 +5.6%p는 그보다 크지만 넉넉하지는 않다.
- 확률 낮은 고객의 최대 대기는 모든 방식에서 떠나는 기준(10초)과 같아 비교에 쓰지 않았다. 이탈 비율로 손해를 비교한다.
- 실제 트래픽을 시간 압축으로 몰리게 만든 것이라, 실제 세일 때의 접속 패턴(같은 상품에 몰림 등)과 다를 수 있다.
- 기획서의 "구경 중인 고객에게 가벼운 페이지" 부분은 넣지 않았다. 처리 순서만 비교했다.
